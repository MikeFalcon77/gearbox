### High

- **serve_stdio calls IoThreads::join while Connection is still in scope, so the writer channel never disconnects and the join deadlocks on every clean exit.** — `crates/gearbox-rpc/src/lib.rs:201` (`RUST-CONC-001`)
  - **Why:** `connection` is still alive at this point, so this join never returns. `IoThreads::join` waits on lsp-server's message-dropper thread, which waits on the writer thread, which is parked in `writer_receiver.into_iter()` because the only sender is `connection.sender`. After the client sends `exit` the process hangs here instead of returning to the CLI. `drop(connection)` before the join, or move the receive loop into a helper that takes the connection by value the way lsp-server's own example does.
  - **Fix:** Drop `connection` (or move the receive loop into a function that owns it) before calling `io_threads.join()`.
- **Both failure branches of `open_roots` and the `failed_roots` field of `InitializeResult` are untested.** — `crates/gearbox-rpc/src/lib.rs:228` (`RUST-TEST-001`)
  - **Why:** No test opens a root that does not exist or two roots that collide on an id, so neither `FailedRoot` push runs and `failed_roots` in `InitializeResult` is never asserted anywhere. The comment above records that `.ok()` used to stand here and discard the cause; a change back to it would keep every test in `initialize_tests.rs` green while roots vanished from the list with nothing reported to the client.
  - **Fix:** Add an `initialize` test with a missing directory and one with two roots sharing a source id, asserting `failed_roots` names both with their causes.
- **Undecodable notification params are logged to stderr only, leaving the server's document copy stale and the client uninformed.** — `crates/gearbox-rpc/src/lib.rs:338` (`RUST-ERR-001`)
  - **Why:** A malformed notification is reported only on stderr, which the client cannot read. For `didChange` that is worse than silent: the stored document keeps its previous text and nothing is republished, so the editor keeps markers computed from text the buffer no longer has. The incremental-change branch handles its own client mistake by sending `gearbox/log`; this path has the same channel available.
  - **Fix:** Report the decode failure to the client over a `gearbox/log` notification as the incremental-change branch does, and name the document that was not updated.
- **The owning source root of a description is re-derived in the RPC layer by nesting depth, while the engine's catalogue attributes it by roots-list order, so the two can pick different `load()` boundaries for the same file.** — `crates/gearbox-rpc/src/lib.rs:398` (`RUST-ARCH-001`)
  - **Why:** This picks the deepest matching root, but `load_catalogue` attributes a discovered `gear.gdl` to the root it was walked from and keeps the *first* declaration in roots order, so with nested roots the editor evaluates the file against a different `load()` boundary than the catalogue entry used. A `load("//...")` that the catalogue's surviving entry resolved can then be underlined here, which is the disagreement the comment above says this ordering prevents. Which root owns a path is the engine's rule, so it should answer it instead of having it recomputed from component counts.
  - **Fix:** Add an engine function that answers which source root owns a path, using the same rule `load_catalogue` applies, and call it from `document_diagnostics` instead of selecting by component count.
- **The client-supplied `out` on gearbox/product/lock is never validated against the workspace or source roots, and the file it names is echoed back in full.** — `crates/gearbox-rpc/src/lib.rs:892` (`RUST-SEC-001`)
  - **Why:** `params.out` goes straight into `default_out_root` with no boundary check, and `compare_to_disk` then reads `<out>/product.lock` and returns its bytes verbatim in `LockResult.on_disk.canonical`. `prepare_generate` runs the same client field through `writable_out_root` before using it, so the client can read any `product.lock` on the machine through this method and not through generate. The field's own doc says it exists so a test can point somewhere else, which is not a reason to accept it unchecked off the wire.
  - **Fix:** Pass `params.out` through `writable_out_root` before joining `product.lock` onto it and refuse with `EDIT_REFUSED` when it is outside the declared boundary.
- **A missing output root is downgraded to an empty `lock_path` sentinel instead of a refusal, contradicting the field's documented contract.** — `crates/gearbox-rpc/src/lib.rs:909` (`RUST-ERR-001`)
  - **Why:** When neither `out` nor a workspace was declared, `default_out_root` returns `None` and the client gets `lock_path: ""` with `on_disk: null`. `LockResult::lock_path` is documented as reported even when absent precisely so "there is no lock yet" and "I did not look" stay distinguishable, and an empty string is exactly the unanswerable case it was meant to prevent. `prepare_generate` refuses the same condition with `GENERATE_REFUSED`.
  - **Fix:** Return an error naming the undeclared workspace, the way `prepare_generate` does, instead of sending an empty `lock_path`.
- **The `AddPlugin` edit, whose contract is to append without destroying existing plugin config, has no test.** — `crates/gearbox-rpc/src/lib.rs:1103` (`RUST-TEST-001`)
  - **Why:** `ProductEdit::AddPlugin` has no test in the crate, while `SetPlugins`, the variant it exists to avoid, is covered in `preview_tests.rs`. The documented reason for this arm is that attaching must append instead of rewriting the list and dropping the `profiles` and `config` on entries already there, and nothing would fail if this line called `set_gear_plugins`. Can we add a batch that attaches a plugin to a gear that already has configured ones and assert their config survives?
  - **Fix:** Add an `apply_product_edits` test with `ProductEdit::AddPlugin` against a gear with configured plugins and assert the existing entries keep their `profiles` and `config`.
- **create_product's write gate is bypassed whenever dry_run is set, so a read-only session can read .gdl contents and probe path existence; the gate is duplicated across five handlers, which is how the copies diverged.** — `crates/gearbox-rpc/src/lib.rs:1210` (`RUST-SEC-001`)
  - **Why:** `dry_run` lets a session that declared no write capability past the gate, and the clone branch below then reads the source `.gdl` and hands its full text back in `after`. `edit_gear` and `edit_with` refuse the dry run too, for the reason written above `edit_gear`: a client without write capability should not learn anything about which paths exist. The gate should be `!state.allow_writes` alone, with `dry_run` decided after it. The durable fix is structural: this gate is spelled out in five handlers (`edit_gear` 941, `edit_with` 1139, here, `scaffold_gear` 1380, `generate_apply` 2270) and the copies have already diverged, so it belongs in one function that takes `dry_run` and decides once.
  - **Fix:** Refuse when `state.allow_writes` is false regardless of `params.dry_run`, matching `edit_gear` and `edit_with`, and move the gate into one shared function called by every mutating method.
- **Validator error from `GearId::new` is dropped in favour of a hardcoded message.** — `crates/gearbox-rpc/src/lib.rs:1389` (`RUST-ERR-001`)
  - **Why:** The `GearId::new` error is discarded and replaced with a fixed sentence, so a client is told the rule but not what was wrong with the id it actually sent. `create_product` formats the validator's own refusal into its message; this path can do the same.
  - **Fix:** Match on the `Err` and include the validator's message in the `EDIT_REFUSED` response.
- **`unreachable!()` in a request handler relies on a path validity invariant established in a different function.** — `crates/gearbox-rpc/src/lib.rs:1456` (`RUST-PANIC-001`)
  - **Why:** `rel` comes from `scaffold_gear_files`, so this holds for today's three literals, but the invariant sits in another function while the panic sits in a request handler. A fourth scaffold file whose path `RelPath` rejects turns one client request into a process panic, and that takes the stdio server down for the whole editor session.
  - **Fix:** Have `scaffold_gear_files` produce `RelPath` values directly (or return the refusal) so this call site cannot panic.
- **`map_err(|_| ...)` discards the source error from `GearId::new`.** — `crates/gearbox-rpc/src/lib.rs:1523` (`RUST-ERR-001`)
  - **Why:** `map_err(|_| ...)` throws away what `GearId::new` said and substitutes a fixed sentence, so the reason the id was rejected never reaches the response.
  - **Fix:** Format the validator's error into the returned message instead of ignoring it.

- **A serialization failure in `notify` is logged to stderr and reported to callers as success.** — `crates/gearbox-rpc/src/lib.rs:2669` (`RUST-ERR-001`)

### Medium

- **`ServeError` variants hold stringified causes, so the source error is discarded at every construction site.** — `crates/gearbox-rpc/src/lib.rs:63` (`RUST-ERR-001`)
  - **Why:** Both variants carry a `String`, so all three construction sites in `serve_stdio` do `e.to_string()` and the underlying io or channel error is gone from the chain. Whoever prints a `ServeError` gets one flattened sentence and no source to walk.
  - **Fix:** Hold the real error types with `#[from]`/`#[source]` on the variants instead of a `String`.
- **didChange inserts documents that were never opened, so entries with unbounded client-supplied keys and text are never removed.** — `crates/gearbox-rpc/src/lib.rs:297` (`RUST-SEC-001`)
  - **Why:** `didChange` inserts for a URI that was never opened, so the argument in `State::documents` that LSP guarantees a `didClose` for every `didOpen` does not hold for these entries and nothing ever removes them. Key and text are both unbounded client strings, so a client that only sends `didChange` grows this map for the life of the process.
  - **Fix:** Replace text only for a URI already present in `state.documents` and report the unopened `didChange` on stderr instead of inserting.
- **didChange triggers a full document evaluation per notification with no coalescing of superseded edits, on the single thread that also serves requests.** — `crates/gearbox-rpc/src/lib.rs:298` (`RUST-PERF-001`)
  - **Why:** Every `didChange` runs a full parse and evaluation on the request thread, and nothing coalesces them. A burst of keystrokes is evaluated once per event even though only the newest text matters, and `product/resolve` or `generate` queue behind all of them, since this loop is the only thread. Draining queued `didChange` for the same URI off `connection.receiver` before evaluating would skip the superseded edits.
  - **Fix:** Drain pending didChange notifications for the same URI and evaluate only the newest text before publishing diagnostics.
- **The not-initialized and no-open-root guards exist twice, inlined in the `catalogue/load` arm and in `require_ready`, with duplicated message text.** — `crates/gearbox-rpc/src/lib.rs:426` (`RUST-ARCH-001`)
  - **Why:** This arm repeats `require_ready` inline, both guards and both message strings. `require_ready` already returns `Option<Response>`, so this arm can call it and fall through to `catalogue_load`, which is what its own doc comment says it was factored out for.
  - **Fix:** Call `require_ready(state, &id)` at the top of this arm and delete the inlined copy.
- **The dispatch arm applies the session readiness guard to `product/create`, re-coupling it to `state.roots` that `creation_boundary` exists to decouple it from.** — `crates/gearbox-rpc/src/lib.rs:539` (`RUST-ARCH-001`)
  - **Why:** `create` needs no session source root once a `creation_boundary` is declared, since `creation_out_root` judges it against the boundary, but `require_ready` here still refuses whenever `state.roots` is empty. A start-screen session that declares a boundary and no roots gets `WORKSPACE_NOT_OPEN` from the one method the ADR says must not be judged by the session, and the write-gate tests call `create_product` directly so nothing pins this.
  - **Fix:** Split the readiness guard so `create` is gated on `initialized` only, and let `creation_out_root` decide the boundary.
- **create_product validates id and profile_id but writes params.version unchecked, unlike the scaffold path which requires a semver triple.** — `crates/gearbox-rpc/src/lib.rs:1234` (`RUST-SEC-001`)
  - **Why:** `id` and `profile_id` are validated here, `version` is not, and it is written into the description either as a rendered template field or stamped onto a clone. `scaffold_gear_files` runs `is_semver` on the same field, and `product()` does not check it, so this is the one wizard field that can carry anything through to a written file.
  - **Fix:** Reject with `EDIT_REFUSED` when `!is_semver(params.version.trim())`, beside the two id checks.
- **scaffold_gear's write gate is bypassed by dry_run, letting a read-only session probe filesystem layout through refusal messages.** — `crates/gearbox-rpc/src/lib.rs:1380` (`RUST-SEC-001`)
  - **Why:** Same hole as `create_product`: with `dry_run` set, a session that never declared write capability reaches `writable_out_root` and `out_root.exists()`, so it can walk arbitrary destinations and read back which ones exist and which are inside a source root from the refusal text. `edit_with` refuses the dry run as well, and this method should too.
  - **Fix:** Refuse when `state.allow_writes` is false regardless of `params.dry_run`.
- **The default generated-tree layout is computed independently in gearbox-rpc and gearbox-cli rather than owned by the engine's generate module.** — `crates/gearbox-rpc/src/lib.rs:2089` (`RUST-ARCH-001`)
  - **Why:** The `.gearbox/<product>/<profile>` layout is spelled here and again in `gearbox-cli/src/generate.rs` (`OUTPUT_DIR`), with nothing tying the two together. It matches today, so `product/lock`'s `on_disk` diff finds the tree the CLI wrote; change the layout in one crate and the diff compares against a directory nobody writes, and reports the lock as missing rather than stale.
  - **Fix:** Move the default output layout into `gearbox_engine::generate` beside `base_root_for` and have both the CLI and this crate call it.
- **generate_file plans the entire generated FileSet to obtain one file's plan, re-reading and re-digesting the whole out tree on every single-file request.** — `crates/gearbox-rpc/src/lib.rs:2343` (`RUST-PERF-001`)
  - **Why:** This plans the whole generated tree to answer about the single path in `params.file`. `generate::plan` stages every entry, which reads each target file off disk, clones its bytes, and then walks the out tree for orphans, and the diff view calls `gearbox/generate/file` once per file the person opens. Can we stage just the requested entry instead of the full `FileSet`?
  - **Fix:** Plan only the requested entry in `generate_file` by passing a FileSet containing that one path, instead of the full `prepared.files`.

- **The staged catalogue load emits one PROGRESS notification per gear on a rendezvous channel, doubling wire traffic and stalling the load on stdout for each one.** — `crates/gearbox-rpc/src/lib.rs:2556` (`RUST-PERF-001`)

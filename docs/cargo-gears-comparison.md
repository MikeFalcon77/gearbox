# Gearbox и `cargo-gears`

## Зачем этот документ

Два инструмента для одной платформы. Этот документ отвечает, чем они различаются и где
пересекаются, чтобы решение об их судьбе принималось по измеренным фактам, а не по
впечатлениям. Сравнение ведётся с точки зрения **инструмента скаффолдинга проектов на
gears** — так был поставлен вопрос, — но границы этой рамки оказались важнее её содержимого,
и об этом первый раздел.

## 1. Рамка неверна, и это главный факт

Инструменты не конкурируют. Они находятся в отношении «предок — предложенный потомок»,
и это записано в самих репозиториях.

**Vision Gearbox лежит внутри `cargo-gears`** — `design/ideas/gearbox-builder-vision.md`,
3379 строк, статус «Vision / pitch document». Наша копия в `docs/gearbox-builder-vision.md`
разошлась с оригиналом на 524 строки диффа, в основном правкой про проекцию фактов из
Rust-атрибутов (ADR-0002).

**Vision прямо велел следовать чужому UX** — §97: «Exact UX should follow the existing
`cargo gears` tool», со списком предлагаемых команд `cargo gears inspect|validate|resolve|
explain|build|generate|deploy`. Поставлено иное: отдельный бинарь `gearbox` с восемью
подкомандами, из которых с `cargo-gears` совпадает по имени только `generate`, и значит она
другое.

**Рядом лежит документ, отвергающий ключевое решение.** `design/ideas/gears-product-configurator-OLD.md`
в разделе «Not Doing (and Why)» отвергает Starlark: «intent fits in TOML, the catalogue is parsed
from code; a language subsystem with no consumer». Более новый vision выбрал Starlark. Оба
документа лежат в одном каталоге, и расхождение нигде не разрешено.

**Как инструменты скаффолдинга они почти не пересекаются.** У `gearbox` **нет ни одной
команды скаффолдинга в CLI**: `catalogue`, `rpc`, `plugins`, `resolve`, `validate`, `product`,
`generate`, `lock` — все читают или генерируют из готового описания. Создание гира живёт
только в RPC (`gearbox/gear/scaffold`), то есть доступно исключительно из Studio.

## 2. Фичи

Знак «—» означает отсутствие, а не слабую реализацию.

| Задача | `cargo-gears` | Gearbox |
|---|---|---|
| Создать рабочее пространство | `generate workspace` (алиас `new`) | — |
| Создать крейт гира | `generate gear` | только по RPC, из Studio |
| Создать описание продукта | `Gears.toml` руками или из шаблона | RPC `product/create` + мастер клонирования, из Studio |
| Создать рантайм-конфиг | `generate config` из трёх `const`-строк | выводится из лока |
| Сгенерировать запускаемый сервер | `.gears/<app>-<env>/` — 2 файла | `.gearbox/<product>/<profile>/` — воркспейс, крейт на процесс, конфиги, Dockerfile'ы, Helm-чарт, `product.lock` |
| Собрать, запустить, тестировать, задеплоить | да, оркестрирует cargo, nextest, llvm-cov, docker | — только генерация |
| Docker | пишет `Dockerfile`, если его нет, и зовёт `docker build` | Dockerfile на процесс, `.dockerignore`, `build.sh` |
| Helm | — | umbrella-чарт, подчарт на процесс, `values.schema.json`, операторские values |
| Разрешение топологии | capability → провайдер, всё в **один** бинарь | несколько процессов, биндинги, транспорты, кластерные провайдеры, профили |
| Файл блокировки | — | `product.lock` с хешем и канонизацией |
| Объяснение решений | — | граф объяснений, диагностики с кодами и evidence |
| Watch-режим | да, с эскалацией restart → regenerate | — |
| Инспекция исходников | `src`, `help topic` (15 тем) | — |

**Вывод по фичам.** Как скаффолдер `cargo-gears` впереди безоговорочно. Как композитор и
генератор развёртывания Gearbox находится в другой категории: `cargo-gears`
разрешает возможности в один монолитный бинарь и не моделирует ни процессы, ни транспорты,
ни развёртывание.

## 3. Архитектура

| | `cargo-gears` | Gearbox |
|---|---|---|
| Объём | ~13k строк Rust (без lints), 3 крейта | ~45k Rust в 7 крейтах + ~22k TypeScript |
| Промежуточное представление | нет; `ResolvedManifest` живёт в памяти | типизированный IR в отдельном крейте |
| Резолюция | пересчитывается каждой командой | сериализуется в `product.lock`, всё выводится из него |
| Ошибки | `anyhow` сплошь, без типов и кодов | коды диагностик, severity, `evidence` с `file:line` в gears-rust |
| Отношение к cargo | оркестрирует: cargo, nextest, llvm-cov, docker | не зовёт cargo вовсе |
| Формат описания | TOML (`Gears.toml`) | Starlark (`product.gdl`, `gear.gdl`) |

**Различие, которое определяет всё остальное: у `cargo-gears` нет лока.** Gearbox
сериализует резолюцию и обязуется выводить каждый артефакт только из неё
(`cpt-gearbox-fr-lock-single-source`) — классическая схема «разреши один раз, отрисуй много»,
как `Cargo.lock`, Bazel, Nix, `terraform plan`. Практическое следствие видно на одной кнопке:
у Gearbox `--dry-run` действительно сухой, у `cargo-gears` **`--dry-run` пишет файлы и правит
корневой `Cargo.toml`, а потом печатает JSON**: `BuildParams::run` зовёт
`generate_server_structure` первой строкой и проверяет флаг только после
(`crates/cargo-gears-core/src/build/mod.rs:174-183`).

**Пересечение, которое стоит назвать прямо.** Модель продукта существует дважды:

1. Оба генерируют запускаемый Cargo-проект в игнорируемый git каталог, ключёванный
   парой: `.gears/<app>-<env>/` против `.gearbox/<product>/<profile>/`.
2. Оба имеют манифест, перечисляющий гиры приложения: `[apps.x.dev].gears[]` против
   `gears = [use_gear(...)]`.
3. Оба делают разрешение «нужна способность → нужен провайдер»: `auto_resolve_system_gears`
   против замыкания и биндингов резолвера.

Это не сходство формулировок, а два независимых резолвера над одной предметной областью.

## 4. Удобство использования

**`cargo-gears`**: ставится одной командой с crates.io, живёт как подкоманда cargo, весь
цикл разработки закрыт одним инструментом, инспекционные команды умеют `--format json`,
а `--format cargo-flags` печатает `-p a -p b` для подстановки в shell.

Против него — измеренное:

- **Жёсткая зависимость от `$CARGO`**: `cargo_cmd()` завершается с ошибкой, если переменной
  нет, поэтому бинарь непригоден в скрипте, контейнере или CI-шаге, где его запускают напрямую.
- **Плейсхолдеры шаблонов спрашиваются только интерактивно.** В `cargo-generate` не
  передаётся `--define`, неинтерактивного пути нет.
- **Документация расходится с кодом** в командах, которые набирают первыми. README:58-59
  учит `generate module` и `config mod`, а `GenerateCommand` знает только
  `Workspace | Gear | Config` (`crates/cargo-gears/src/generate.rs:188-195`), алиаса `module`
  нет.
- **Флаг `--name` у `build` и `run` не действует.** Он объявлен и задокументирован
  (`crates/cargo-gears/src/common/mod.rs:78`), метод билдера существует, и `.name(args.name)`
  вызывается трижды — все три раза внутри `mod tests`. Продуктовая цепочка
  (`crates/cargo-gears/src/build.rs:15-18`) ставит `.app()` и `.env()` и `.name()` не зовёт,
  поэтому тесты зелены, а флаг игнорируется.
- **`generate config -t prod` выпускает ключ `modules:`** (`generate/config.rs:48`, `:73`),
  которого в `AppConfig` нет — там `gears` (`app_config.rs:28`), — а сама структура не
  `deny_unknown_fields`, так что секция гиров молча теряется. Шаблон `dev` при этом пишет
  правильный `gears: {}` (`:22`).
- **Шаблоны по умолчанию тянутся с личного GitHub-аккаунта по SSH** —
  `git@github.com:Bechma/cf-template-rust.git`, продублировано в двух файлах
  (`generate/mod.rs:5`, `list/templates.rs:8`).

**Gearbox**: диагностики с кодами и evidence на `file:line` в корпусе — это
заметно лучший опыт разбора ошибки, чем строка `anyhow`. `--format json` есть у большинства
команд.

Против него — тоже измеренное:

- **Установить нечем**: `publish = false`, проприетарная лицензия.
- **CI нет вовсе** — каталога `.github/workflows` не существует. У `cargo-gears` шесть
  воркфлоу, release-plz, пять релизов за три недели, четыре контрибьютора.
- **Нет changelog и релизного процесса.**
- **Скаффолдинг недоступен из терминала.** Авторская работа возможна только в Theia Studio.
- **Корпус о нём не знает**: `gears-rust` не упоминает `gearbox` нигде, тогда как
  `cargo-gears` присутствует в `Gears.toml`, `Makefile`, `CONTRIBUTING.md`, `README.md` и
  в скилле `gear-creator`. Оговорка: большинство этих ссылок — про lint, который исключён
  из рассмотрения; вне его остаются `ls features`, `tools check-version` и `cargo install`
  в Makefile.

## 5. Расширяемость

Здесь преимущество у Gearbox, и оно структурное.

**`cargo-gears` расширяется только правкой самого инструмента.** Реестр системных гиров —
`SYSTEM_REGISTRY_GEARS`, пятнадцать имён константой в коде; добавить гир — значит выпустить
новую версию CLI. Три шаблона конфига — `const`-строки, `match` по трём именам. `TemplateKind`
и `GenerateCommand` — закрытые перечисления. Реестр шаблонов в манифесте есть, но **не может
перекрыть встроенный шаблон** (поиск идёт сначала по встроенным), а объявленные в нём виды
`config` и `agents` не читает никакой код. Плагинов нет и по дизайну не планируется.

**Gearbox не имеет реестра гиров вообще** — каталог проецируется из Rust-атрибутов
сканированием исходников (ADR-0002). Добавление гира в платформу не требует изменения
инструмента. Оверлей шаблонов объявляется продуктом путём наружу, ключуется, и генератор
сообщает, какие шаблоны переопределены. В схеме values есть открытый объект `custom` —
единственное место, где закрытая схема сознательно оставляет дверь для чужого шаблона.

## 6. Идиоматичность и отраслевая практика

**`cargo-gears` идиоматичен для своего жанра.** Подкоманда cargo, `cargo-generate` для
скаффолдинга, оркестрация cargo/nextest/llvm-cov, публикация через release-plz — ровно так
устроены `cargo-leptos`, `cargo-shuttle`, `dioxus-cli`. Скаффолдинг делегирован стандартному
инструменту экосистемы вместо собственного движка шаблонов.

**Gearbox идиоматичен для другого жанра** — Bazel/Gazelle, Terraform, Nix, Kubebuilder:
декларативное описание → резолюция → лок → рендер. Его собственный ADR-0010 содержит обзор
Cargo, Kubebuilder, Angular, Rails, dotnet, Yeoman, Copier, Gazelle, Spring Initializr и
Arduino IDE и выводит шестиярусную модель владения файлами.

**По этой же модели у `cargo-gears` есть нарушение, и его стоит назвать.** `manifest validate`
и `ls` — команды чтения — вызывают `Manifest::resolve` по каждой паре app/env
(`manifest.rs:230-234`), а `resolve` зовёт `remove_stale_workspace_members`
(`manifest.rs:325`), который при первом же удалении записывает документ обратно
(`generate/gear.rs:250`). То есть команда инспекции **правит корневой `Cargo.toml`
пользователя**.
Ярус 3 модели разрешает инструменту хирургически править манифест, но командам записи, а не
инспекции. Cargo здесь строг ровно наоборот: `cargo add --dry-run` существует именно затем,
чтобы «не писать манифест».

**И симметрично: у Gearbox нет того, что отрасль считает обязательным** для инструмента
разработчика — CI, релизов, установки, команды `new`. Инструмент, который нельзя поставить и
у которого нет `new`, отраслевой практике не соответствует независимо от качества движка.

## 7. Что каждому стоит взять у другого

**Gearbox — у `cargo-gears`:**

- Команду скаффолдинга в CLI. Авторство только через Studio — барьер входа, которого нет
  ни у одного сопоставимого инструмента.
- Устанавливаемость: CI, changelog, релизный процесс. Без этого сравнение по остальным осям
  академично.
- `cargo-generate` вместо `format!`-строк для крейтов гиров, либо хотя бы форму
  переопределения `--git` / `--local-path`.
- Трёхзначный `--x` / `--no-x` с откатом к манифесту — пять строк, применённых единообразно.
- `--format cargo-flags` для композиции в shell.
- Класть `SKILL.md` в сгенерированное дерево, чтобы проект объяснял агенту, как с собой
  обращаться.

**`cargo-gears` — у Gearbox** (если инструменты сближаются):

- Лок и честный `--dry-run`.
- Типизированные диагностики с кодами вместо строк `anyhow`.
- Проецируемый каталог вместо константы из пятнадцати имён.
- Команды чтения, которые не пишут.

## 8. Что с этим делать

Свидетельства говорят в пользу **разделения по границе, а не слияния или замены**: vision
сам помещает Gearbox «above existing mechanisms», а `cargo-gears` явным нон-голом отказывается
от инфраструктуры и развёртывания. Тогда граница такова:

- **`cargo-gears`** — жизненный цикл крейта: создать, собрать, запустить, протестировать,
  проверить, инспектировать.
- **Gearbox** — композиция продукта: каталог, резолюция, лок, генерация дерева,
  Docker и Helm.

Но у этого решения есть цена, которую надо заплатить явно, иначе граница не удержится:

1. **Модель продукта должна остаться одна.** Сейчас их две — `[apps.x.dev].gears[]` в TOML и
   `use_gear(...)` в Starlark, с двумя резолверами. Пока это не решено, любой пользователь
   платформы обязан знать оба формата.
2. **Имя и точка входа.** Vision просил `cargo gears`; поставлен `gearbox`. Либо следовать
   vision, либо зафиксировать отход и причину.
3. **Расхождение про Starlark** между двумя документами в `design/ideas/` не разрешено. Это
   выбор, определяющий формат описания на годы, и он заслуживает ADR, а не двух питчей.

Эти три пункта — кандидаты в ADR. Настоящий документ решений не принимает.

## Как это проверялось

Сверено по исходникам обоих репозиториев 2026-09-06: `cargo-gears` 0.0.7, Gearbox
0.1.0. Утверждения о чужом коде, звучащие как обвинения — недействующий `--dry-run`,
пишущие команды чтения, мёртвый `--name`, потерянная секция гиров, — перечитаны в файлах
поимённо, а не приняты с чужих слов.

Самое хрупкое здесь — числа: версия, счёт релизов, наличие CI. `cargo-gears` активно
развивается, и эти строки устаревают первыми.
